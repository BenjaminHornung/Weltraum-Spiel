# W07 Factory-Inputzustellung: unabhängige Source-only Kurzprüfung

**Befund:** bestehendes busyRead/latestSlot kann eine kurze Down/Up-Absicht vollständig vor Nativezustellung neutral überschreiben. Eine eigenständige Factory-Intentzustellung ist ein enger technischer Vorschlag, **keine neue IPC-/Writefreigabe und kein Ownerfreeze**. Kein Code, Tests, Builds, Browser, Native-/Profiljobs oder Evidence geändert. Diagnostic68 und Normal67 sind von Root gemeldete Beobachtungen; tatsächliche Workerempfangszeiten sind damit noch nicht belegt. Historische Ninth-/Ghost-/Inputreviews bleiben bytegebunden.

## Tatsächlicher Verlustpfad

`physics/client.ts:424–426` startet per `update()` eine neutrale Read; `207–214` setzt busy, kopiert den Input und wartet auf Reply. Währenddessen setzt `setPlayerInput:369–374` bei Down x≠0/dirty; `readInput:208` postet wegen busy nichts. Up vor Reply setzt denselben Slot zurück auf x=0. Finally sendet ausschließlich diesen neuesten neutralen Wert. Ein Sprung unterscheidet sich durch den bestehenden OR-Merge; Bewegung besitzt bewusst kein solches Latch. No-op verhindert unnötige Reads, bewahrt aber keinen bereits überschriebenen Level.

Vorhandene Unit `tests/unit/hvp-player-input.test.ts:108–114` beginnt Down **bei idle Read** und prüft dann Latest-neutral. Sie schließt busy-at-keydown daher nicht. Producer `player/input.ts:61–69,91–100` ruft bereits echte Down/Up/Mouseevents direkt auf und löscht nur Producerjump nach Staging. Deshalb wäre eine weitere RAF-Abhängigkeit oder garantierte Mindesthaltezeit keine passende Korrektur.

Worker `physicsWorker.ts:147,182` wendet nur Input aus Read an und erstellt danach das komplette Snapshot. Private Session `session.ts:334` leitet Input direkt an denselben Charactercontroller; dessen `locomotion.ts:49–66` validiert Werte, speichert Levels, konsumiert Jump und bewegt ausschließlich beim echten bestehenden Fixedstep. Read/Intent darf **niemals** `advance`, Timerclock oder Worldstep ausführen.

## Engster vorgeschlagener Anschluss

Factory-opt-in bleibt das bestehende `factoryEnabled`; Producer-API `setPlayerInput` und Legacydefaults bleiben erhalten. Ein **neuer eng geschlossener Intentnachrichtentyp auf demselben vorhandenen Physicsworker** postet geänderten Level/Jump unmittelbar unabhängig von Snapshotbusy. Worker verarbeitet ihn an der bestehenden privaten Session und antwortet klein **ohne Snapshot, camera, aim, Preparedpublication oder Weltserialisierung**. Bestehende Replies/Clockdiagnostics dürfen keine held/public Authority überschreiben. Kein zweiter Worker oder NativeWorld.

**Factory-Read muss dann inputfrei sein.** Sonst kann eine ältere neutrale Snapshotread nach einem neuen Down den Nativeintent wieder löschen. Legacy-Read behält input. Camera/aim und normale Snapshots bleiben auf ihrem bisherigen Pfad. InputDown und -Up werden in Senderreihenfolge gepostet; **Release wartet nicht auf den InputACK**, sonst verlängert ACK-Latenz die reale Bewegung künstlich. Keine neue unbegrenzte Eventqueue, keine verlängerte Haltezeit und kein Nachholen vergangener Bewegung.

Bestehende **max8 pending und 20000ms Deadline** (`client:194–199`) unverändert beibehalten; neue Intentrequests zählen zum gleichen endlichen Budget. Belegt werden muss, dass Snapshottraffic Releases nicht aussperrt. Eine Factory-only Reservierung innerhalb dieser acht Plätze wäre eine technische Scopefrage, kein Budgetanstieg; deren konkrete Aufteilung ist hier nicht gewählt. Bei erschöpfter Kapazität nicht still einen Release verwerfen oder aktiv weiterlaufen lassen: definierter fail-closed Neutral-/Stopanschluss nötig. Eine nebenbei untracked unbeschränkte postMessage-Queue wäre keine Lösung. Die autorisierte Umsetzung muss diese Endlichkeitsgrenze konkret festlegen.

Die Ursache von Diagnostic68 bleibt teilweise offen: Ein Worker kann auch FIFO-Down/Up nacheinander zwischen zwei echten Timercallbacks abarbeiten; dann ist ΔX=0 korrekt. **Keine garantiert positive Bewegung je125ms-Puls** aus dem Vorschlag ableiten. Vorher/Nachher-Zustellung und actualTick müssen gemessen werden, ohne durch Testinstrumentierung Zeit, Welt oder Inputs zu verändern. Kleinere Intenthandlers können Read-Abhängigkeit entfernen, garantieren aber keine Schedulerinterleaving-/Latenzwerte.

## Pflichtseams

- **Nativeguard:** aktuelle private `factoryEnabled`, disposed, tickRunning/CharacterWalking, staged/terrainHeld, Branch/Moving, `extraHeld` (`session:142`) und Factoryzustand prüfen. `session.input` ist heute unguarded; allein ein möglicherweise veralteter Main-Snapshot reicht nicht. `facilities.busy`, neighbor.busy, residency.held, coverageHeld, bodyResidencyWork liegen bereits privat vor: kein teures Gesamt-`read()` für Input nötig.
- **Pause/Inspect/Play/Stop:** Producer `stop:42–49` leert Keys/Jump und bestellt Pause; Native `session.pause/inspect/play:326–333` neutralisiert über setEnabled. Ausstehende Bewegungs-/Jumpabsichten an dieser tatsächlichen Barrier verwerfen; Resume verlangt neue aktive Bedienung. Ordinary Up erhält genau den unsent Jump, ausdrücklicher Cancel muss auch Native-jumpPending löschen. Native setInput(zero) allein kann das nicht, da `jumpPending ||= value.jump` gilt. Vorhandene enable-Neutralisierung nutzbar; falls enger neutralize-Helper erforderlich, separaten Locomotionpfad ausdrücklich grantpflichtig behandeln.
- **Hold/Replacement:** Worker `restore:109–133` enthält await und kann weitere onmessage-Aufrufe während Prepare empfangen. Intent darf weder alten A noch hidden B beeinflussen. Ein kleiner privater monotonic Inputfence/Generation mit Initialisierungsbindung muss echte Pause/Scene-/Restorebarrieren invalidieren; tatsächlicher Session-ID allein reicht nicht, da A/B dieselbe gespeicherte ID haben können. Der derzeitige Physics-Snapshot enthält keine belegte öffentliche Hostepoch für diesen Zweck; kein neues ungebundenes Feld als vorhandene API ausgeben.
- **FIFO/Stale/Dispose:** aktuelle Workerinstanz/Initializebindung plus sichere Sequenz/Fence prüfen; stale Down/Up darf neue aktive Session nicht neutralisieren oder anstoßen. Gleicher Sender-Port erhält FIFO, async Restore erfordert dennoch Guard. `client:460` closing/clear und worker `77` Dispose bleiben terminal. Late ACK enthält keine snapshot/held-Daten, darf keine neue dirty Zustellung auslösen. Restore-/Holdrejection des neuen Typs muss eng behandelt werden; aktueller Workerdefaultcatch `197–198` entsorgt sonst die ganze Welt.
