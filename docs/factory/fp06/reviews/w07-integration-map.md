## 3. Konkreter minimaler Callgraph (Vorschlag, keine bereits vorhandenen Calls)

1. **Untrusted UI-Kandidat → pure `prepareFactoryPlacement(view,request)`.** Bindung mindestens session/epoch, Terrainrevision/base/sourceDigest, katalog-/installations-/S0Digest, lokale ganzzahlige 250-mm-Koordinaten und 90°-Yaw, Actor-/Zugangsfakten, native Facilityrevision/Owner-Set, BOM-Lots/Materialbinding. Solid-/Sweep-/Service-/Portvolumen sowie alle tatsächlichen Supportpatches gegen denselben aktuellen Snapshot prüfen. Ghost/Escape bleiben projektionell und erzeugen keine echten Materialreservierungen oder nativen Körper. `FP03:339–412` ist explizit: unbekannte Coverage = UNKNOWN, Commit prüft erneut.
2. **Verdeckte Vorbereitung** ist zunächst pure Rezept-/Artifact-/Budgetvorbereitung. Noch keine Worldmutation. Host beansprucht genau einen bounded Construction-Lease; stoppt Avatarinput und erlangt **echtes Pause-ACK** (`host.pause`, aktuell `hvpBootstrap.ts:2174–2177`). Lease blockiert weitere Construction-/Terrain-/Savebefehle, hält aber keine versehentlich permanente WaitingForHost-Schleife. Nach jedem await current / epoch / Revision erneut prüfen. Native hidden Prepare erst jetzt an der sicheren bestehenden World; ein vorheriger rendererbasierter Vorschauzustand ist kein natives Install-ACK.
3. **Joint Preflight und Material-CAS-Kandidat:** von aktuellen Resources einmal `prepareFactoryMaterialStep(materialBase,{kind:"transfer", transactionId, ownerId, moves:BOM→facilityContainer})` bilden. `commitFactoryMaterialStep(materialBase,materialPlan)` liefert einen verifizierten Complete-Candidate/Receipt oder Reject. Der Return ist weiterhin **unveröffentlicht**. `materialBase` muss den leeren Zielcontainer bereits enthalten: W02 erstellt keinen unbekannten Container beim Transfer. Entweder hostseitig vorher definierter leerer installierter BOM-Container oder ein innerhalb derselben Constructiontransaction unveröffentlicht um diesen leeren Container ergänzter MaterialView. Im zweiten Fall bindet der äußere Placement-CAS zusätzlich exakt den ursprünglichen Hostview; die Erweiterung und das pure Material-Prepare/Commit werden aus dem noch aktuellen Hostview erneut aufgebaut. Keinen Plan mit anderem Base gegen `currentMaterial` committen und keinen leeren Zwischencontainer als neue Worldauthority veröffentlichen. Neue Container verwenden dieselben vorhandenen Resources-Definitionen/-Snapshots; Stückinstanzen C26/C03 etc. behalten ihre Originalidentity. W02 bietet noch keinen delete/consume/buildIntent und prüft Gesamtmasse (`reservations.ts:269–274`): eigener Zahlenledger oder Abzug ohne gespeicherte installierte BOM wäre falsch. Materialien aus allen Hostcontainern inkl. installed BOM/WIP werden genau einmal bilanziert; technische Containerkapazität/Volume darf nicht pauschal Infinite werden.
4. **Hidden native Facilityprepare + hidden Renderstage:** jeweilige neue Assets/Collider sind allocated, aber disabled/unsichtbar. Gegen World-/Facility-Membership vor Prepare sowie globale coexistence-Budgets prüfen. Prepare-Receipt bindet ownerId, transactionId, Profil-/Collisiondigest, expectedFacilityrevision, konkrete Memberhandles und den bestätigten pausierten Tick. Renderer-Upserts können scheitern; dann Prepare rollback, bisherige Resources bleiben unveröffentlicht. Erst wenn beide Vorbereitungen vollständig sind darf Nativecommit erfolgen.
5. **Native `CommitFactoryFacility(id)` → CommittedHeld-ACK.** Enable fixed Body/Colliders in **dieser** World; solver bleibt gehalten, öffentlicher Clientread hält das bisherige Snapshot. Kein öffentlich sichtbares Collider-only-Place. Nochmals current Terrain-/Material-/Ownerbinding validieren; bei stale Material-CAS → nativer Rollback, keine refundMutation.
6. **Ein synchroner Hostpublish ohne await:** Host wechselt den kompletten verifizierten MaterialView und die gebundene LogicalFacility-Registry; Client publiziert exakt das gebundene native CommittedHeld-Receipt; Stage veröffentlicht ActiveFacilityKeys/Transforms und gemeinsame Projektion. Original-MaterialView, Ownerregistry, Sichtbarkeit, native Memberhandles und Sourcebindings bleiben bis zum Finalize für den Fehlerpfad erhalten. Artifact-Upsert/Projectiondispatch können Fehler werfen: der Catch darf nicht blind Commit-Erfolg behaupten. Keine Callback darf einen halben Kandidaten als neuen autoritativen Worldzustand konsumieren; nötigenfalls veröffentlichte ReadViews erst nach erfolgreicher Projektion freigeben.
7. **Finalize-ACK → idle/quiescent, explizite sichere Fortsetzung.** Neue Member bleiben owned; Stagingleases/Retired-Vorräte frei; bestätigter Zeitbezug unverändert. W06-D05-Pausezeit gibt keine Produktionsarbeit. Keine automatische Wiederaufnahme aus einem inzwischen versteckten/stale/Recoveryhost. Dispose besitzt auch Pending-/Recoveryassets; `canEndSession` darf keine ausstehenden Rollback-/Finalizearbeiten verschlucken.
8. **Fehler:** Vor joint Publish nur Kandidaten verwerfen/Nativerollback; nach Publish alle vorherigen Original-Snapshots/Owner-/Renderbindungen wiederherstellen, keinen zweiten Materialcommand als frei erfundene Rückzahlung ausführen. Erfolg nur bei vollständigem Beweis der alten Memberidentitäten und Fakten; unvollständiges ACK, verlorene alte Members, unsichere Veröffentlichung oder Retirefehler → sichtbarer terminaler RecoveryHold. Der gleiche transactionId wird anhand beider Receipts idempotent erkannt; nicht nach Timeout mit neuer ID duplizieren. W02 bietet derzeit keine öffentliche administrative `rollbackMaterial`-Mutation: Host kann den unveränderten Originalview als Teil des gehaltenen Jointtransactions verwenden, nicht historisch veröffentlichte Saves rückwirkend umdeuten.

Diese Reihenfolge enthält die geforderte hiddenprepare → jointpause/materialCAS → nativecommit → projectionpublish → finalize/rollback-Architektur, präzisiert aber: **Worldmutierendes hiddenprepare darf nicht vor der echten sicheren Pause starten.** Eine kleine spezifische Constructiontransaction reicht; kein abstrakter Transactionengine-/Cargo-/World-Neubau.
