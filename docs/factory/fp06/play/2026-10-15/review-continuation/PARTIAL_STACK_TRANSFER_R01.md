# Compatible partial stacks — existing transfer seam

Root decision, 17 October 2026. Review item5C is reproduced in source: the existing production admission, Host intent and reservation creation require one stack per recipe input; normal Transfer currently always requests a new target ID, so compatible2kg and6kg RAW cannot become the required8kg input through that flow. This is a confirmed gameplay integration gap, not authority to extend ProductionStart or stored formats.

Reuse resources/transfer.ts's exact hasCompatibleMetadata predicate by exporting that existing function. In factory/session/cargoHandling.ts's ordinary transfer branch only, select the first already sorted compatible bulk target stack if one exists; otherwise preserve the current deterministic whole/source or partial/ui_*_lot target ID. The mature transferResource path rechecks the exact metadata and performs the merge. Owner, resource, grade, condition, legal status, mission, sealing and full extensions must match. Never combine different production provenance. Pickup, deposit, return, carrier full-custody restrictions, capacity, CAS, history and atomic rollback keep their existing guards.

Acceptance is ordinary2kg Transfer into compatible6kg input producing one8kg stack with unchanged total mass and an actual target-ID receipt; unchanged single-stack REC01 then yields7.5kg semi plus0.5kg offcut. Mismatched owner/grade/condition/extensions must stay separate. Insufficient capacity is atomic and command replay transfers nothing twice. The existing carrier partial-unload refusal remains. No recipe, public schema, canonical Golden, resource or Clock changes. This is one bounded integration candidate; root owns review and tests.
