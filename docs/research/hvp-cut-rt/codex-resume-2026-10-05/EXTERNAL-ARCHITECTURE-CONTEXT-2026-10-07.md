## 1. Product landscape and ownership

The active product is apps/weltraum-browser, TypeScript in the browser, Vite8.1.5, Three.js0.185.1/WebGL and Rapier3D-compat0.12.0/WASM. TypeScript7.0.2, Vitest4.1.11, Playwright1.61.1; task commands use pinned Node22.23.2. No server-side cut service or active Unity runtime is involved. The repository also contains separate flight/navigation/autopilot/gameplay modules and a Surface Lab. main.ts selects these routes; ?hestiaPrototype=1 lazily mounts Hestia through hvpRoute.ts/hvpBootstrap.ts. Combined SurfaceLab/Hestia queries prefer Surface Lab. TestBridge is optional and excluded from real gameplay evidence.

hvpBootstrap is the current composition root: source/save loading, initial mesh/collision preparation, physics client, render backend and profiles, HUD/player/camera/tool, terrain/structural/moving consumers, neighbor/residency, save/load and RAF loop. There is substantial orchestration here. UI reads projections and sends commands; it is not Source or World authority. Three.js meshes, collider handles, diagnostics and transport objects likewise do not create canonical truth.

The versioned Coast primary has256x128x256 slots,8,388,608 cells at0.125m, and four material roles. TerrainRoot holds source identity/session/epoch/revision/digest and sparse COW16-cubed leaves. Adaptive/structural code models canonical bricks/cells/materials, command effects, connectivity/anchoring, classification, mass/COM/inertia, physics transition and rigid recipes. These are shared beyond Hestia and have strict generic getter/Proxy/Species/error/hash contracts. Fragment mesh, collider and world objects derive from the canonical Source. Render look/AO/water/vegetation are existing projections; no quality reduction or P02 vegetation optimization is adopted.

One separate physics Web Worker owns the persistent Rapier World. Simulation uses1/60s fixed steps with bounded catch-up and visible SimulationHold. Initial collision preparation uses a temporary bounded compute pool which shuts down before simulation-worker startup. The persistent terrain compiler owns a reusable general compute pool of one or two Web Workers, queue32, for terrain/collision/support/body mesh/neighbor jobs. These are not32 parallel threads. Parent phase accounting and admission bound concurrent heavy work; Main performs orchestration and some shared validation/encoding/copying/hash work.

## 2. Static terrain cut pipeline

Normal pointer/key input -> player/tool Aim+Preview -> existing picker -> revision/source-bound Box/Sphere/Cell request with commandId -> terrainConsumer. The consumer preserves idempotent receipts, serial mutation/backpressure and rejects stale/recovery-held input.

TerrainRoot.prepare produces one before/after COW plan. Safe quarry cuts retain anchored terrain. Rockarm undercuts use complete support/connectivity analysis: build a complete slot snapshot, hash/admit/transfer to Support worker; search connected/support components; ingest disconnected canonical fragments; fully classify and derive masses/rigid recipes/collider boxes; encode/hash/return a bounded result. Main checks terminal ownership, input binding, full output digest and semantic result. Transfer preparation removes detached cells from terrain and binds their body identities, rather than leaving terrain and dynamic body simultaneously authoritative.

Terrain compiler remeshes affected sectors including halo/boundary/AO/material behavior and creates collision products through workers. Data transfer uses explicit typed buffers and ownership; private codecs and hashes are bounded but still traverse full payloads. One retained support plan and one finite shared phase-credit account accompany derived work; this is not a new Source or a renderer truth certificate.

Physics prepare now has two distinct parts. Source-only PrepareTerrainPlan validates/ingests real fragment Source and recipes before pausing the World. It is bound to current native owner, requestId, incarnation, session/epoch, generation and digest. Read/tick/input can continue during this Source preparation. The ACK contains only exact recipe-derived Source views: ownerId,digest,COM,cellCount,mass,colliderCount,sourceBytes; it does not fabricate an admitted World body or pose.

For the owned detached-fragment path, Main prepays graphics/copy coexistence against the same budget, awaits Source ACK, and stages fresh hidden graphics BEFORE NativeStage. R116/R117 use the existing2ms MessageChannel task pump,4096-byte typed folds/copies, exact existing mesher and material regrouping. Current Root/mount/epoch is checked at every advance. Each candidate gets a fresh ephemeral render key; accepted uploads remain hidden. Actual NativeStage consumes the exact prepared ticket, performs collider/body installation in the existing World, and starts the short actual World hold. Actual Stage Source views must equal the earlier recipe views before commit.

Then Native commit, Root commit, render visibility publication, Native publication/finalize and old-generation cleanup form a coordinated transaction. Root/World/render revisions must agree. Failure restores the previous generation; proven rollback permits retry only with a fresh commandId. Unproven native/renderer restoration or release enters RecoveryHold and retains owned resources/credits. Dispose/Restore drain exact pending work and late replies before freeing the World. No new Rapier World is created as a normal Cut shortcut.

## 3. Moving bodies and rendering

A hit on a dynamic fragment/descendant goes through bodyCutConsumer and the physics owner, not TerrainRoot. Current owner/digest/local cells and native pose/motion are checked. B1 retains one owner-local cut plan with complete command effects, child Source, classification/mass/rigid recipes and accounting. Child mesh work uses the reusable compute pool. Workers return derivatives; Main/native owner binds them back to the exact retained child and validates complete mesh geometry before Stage. A matching hash alone is insufficient. World pose, motion, mass, collider installation and authoritative commit remain owned by the simulation worker. Parent and children must not be visible simultaneously. A separate existing structural/timber path and foliage support remapping remain in the landscape.

Presentation uses MeshArtifact -> RenderCommand -> ThreeRenderBackend -> resource registry/material factory/BufferGeometry -> frame projection/visibility plan -> RAF render. Source and artifact revisions, content hashes, backend revision, immutable metadata, exclusive full buffers, ranges/material coverage and bounds are checked. SnapshotOwned artifacts copy inputs; exclusive adoption is an explicit separate contract. Render visibility and frame bookkeeping are shared even for the owned asynchronous path.

All FIVE complete large-buffer hash passes currently remain: initial artifact content hash, artifact validator, command-construction validator, backend-dispatch validator, and full command signature including typed arrays (only ownership omitted). The last patch bounds these passes rather than eliminating them. Source/structural canonical hashes and transfer checksums are additional passes with their existing byte formats. R117 fixed cancellation after an accepted hidden upload: exact backend geometry and extra plain material leases must both release; a failed lease release remains tracked/RecoveryHold. There are no new hash certificates, mutable-array hash caches or memoized classification results in this checkpoint.

Persistence uses versioned canonical game/world/grid/body/plant/receipt codecs and IndexedDB, including live save/load and cold reopen. It binds primary Source, neighbor state, player/camera, bodies/motion, plants, receipts, generations and solver/look/source profiles. Restore is its own transaction. These identities and invariants cannot be casually replaced with scene-only save data.

## 5. Discussion request

Investigate whether the architecture can meet the end-to-end goal, rather than prescribing more isolated micro-optimizations. Read the checkpoint first; separate facts, hypotheses and required measurements. Evaluate two or three alternatives and recommend a path, with authority/ownership, transfer volume, repeated validation/hash work, worker scheduling, render upload and atomicity as explicit dimensions.

Consider whether a persistent worker-owned canonical terrain/structural state with version-bound delta commands, more local incremental connectivity/meshing, combined Source/recipe work, or redesigned trusted internal admission can avoid repeated reconstruction/full transport while preserving public contracts. Consider whether process boundaries and transaction order should change, or whether current validation crossings are genuinely necessary. These are options for debate, not already-implemented or automatically-authorized changes. State when an option needs a changed internal protocol or approval of a changed public/Save/semantic contract; do not silently skip checks or lower geometry/quality/caps.

Ask for the smallest discriminating experiments with comparable full workloads and trace points; give migration stages, rollback risks, complexity and expected bottleneck removal. Address both static undercut/detach and moving-body recuts, cold/warm/save/restore, failure/cancel/reset/dispose and stale replies. A new architecture should simplify the overall chain, not add another parallel authority/cache/ledger. No code changes yet: return a decision brief for the human to discuss and then send back to the implementing agent.
